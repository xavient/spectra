Module 1

SDD Foundations

What spec-driven development actually is, the three levels of commitment, the four-phase workflow, and the honest case against adopting it.

Time 45 min
Format Reading + knowledge check
Prerequisites None

Learning objectives

By the end of this module, you will be able to:

  1. Define what a “spec” is in spec-driven development, and how it differs from a PRD or detailed prompt.
  2. Identify which of the three SDD levels (spec-first, spec-anchored, spec-as-source) fits a given situation.
  3. Walk through the four-phase SDD workflow (Specify → Plan → Tasks → Implement) and describe what each phase produces.
  4. Recognize when SDD adds value and when it's overkill.
  5. Articulate the main critiques of SDD honestly enough to push back when adoption is being oversold.

1.Why this is happening now

For decades, code has been the source of truth in software development. We write requirements docs and they drift. We draw architecture diagrams and they rot. We write tests, often after the fact. The code — whatever it actually does — becomes the de facto truth of the system, and “what should this function do?” gets answered with “read the code.”

That stayed manageable as long as humans were the bottleneck on writing code. AI coding agents have changed that. When an agent can produce a working endpoint in 30 seconds, the bottleneck shifts upstream. The new constraint is: how clearly can you state what you actually want?

Spec-driven development is the answer to that question. Rather than typing increasingly elaborate prompts into a chat window, you write a structured specification first, and the agent uses it as the authoritative description of what to build.

The simplest way to put the inversion (from Piskala's 2026 paper):

In spec-driven development, code is the implementation detail of the specification — not the other way around.

That's the whole idea. Everything below is detail.

2.What is a spec, exactly?

You're going to hear “spec” used loosely in tutorials, vendor blog posts, and Twitter threads. Some people use it to mean “a slightly longer prompt.” Others mean “a regenerated copy of the codebase in markdown form.” Neither is what we mean.

For this course, a spec has three properties:

  1. Structured. It follows a known format, not just prose. Sections for outcomes, scope, constraints, verification.
  2. Behavior-oriented. It describes what should happen, not how it's implemented.
  3. Executable. It is consumed by tooling — AI agents, CI gates, contract tests — not just read by humans.

That third property is what separates a spec from a PRD or a design doc:

ArtifactRead byEnforced?Update cadence
PRDProduct, engineeringNo — humans interpret itOften stale within weeks
Design docEngineering peersNo — point-in-time reviewRarely updated
Detailed promptOne AI agentNo — vanishes after the chatPer-conversation
SDD specAI agent + CI pipelineYes — build fails on divergenceLiving, updated as work progresses

A spec is supposed to fail your build when reality diverges from it. That's the bar.

What a spec is not

  • It is not a code-shaped artifact. If your spec reads like pseudo-code, you've gone too far down toward “how” and lost the abstraction.
  • It is not exhaustive. You don't spec everything. You spec what's needed to remove ambiguity for the current piece of work.
  • It is not generated and forgotten. If you generate a spec, never review it, and let an agent implement against it, you have a vibe-coding loop with extra steps.

3.The three levels of SDD

Not all SDD adoption looks the same. There are three broadly different commitments, and most of the confusion in online discourse comes from people talking about different ones without realizing it.

Spec-first

The lightest commitment. You write a spec before coding, use it during the work, and after the work ships, the spec may or may not stick around. The win is up-front clarity — you don't let the AI guess.

Use this when:

  • You're new to SDD and want to feel out the practice.
  • You're working on initial feature development with AI assistance.
  • The spec's value is in guiding the build, not in long-term maintenance.

This is where almost every team should start. The lab in Module 3 uses spec-first; the brownfield lab in Module 4 nudges toward spec-anchored.

Spec-anchored

The spec is maintained alongside the code throughout the system's life. When behavior changes, you update both. CI checks ensure they don't drift. If they drift, the build breaks and someone has to deal with it before merging.

Use this when:

  • You're maintaining a long-lived production system.
  • You're in a regulated domain that needs audit trails.
  • Multiple teams or services rely on contracts that need to be enforceable.

This is the sweet spot for most production systems. BDD with Cucumber and contract testing with Specmatic or Pact are well-established examples — both predate “SDD” as a label, both are fundamentally spec-anchored.

Spec-as-source

The spec is the only artifact humans edit. Code is generated from it and treated as a build output, like a compiled binary. If you want to change behavior, you change the spec and regenerate.

Use this when:

  • You have a mature, certified code generation pipeline (e.g., automotive control software via Simulink for ISO 26262).
  • You can confidently throw away generated code and not lose anything.
  • The cost of editing generated code directly would be higher than the cost of strict spec discipline.

This is rare in general business software today. Tools like Tessl are exploring it, but it remains experimental for anything outside narrow domains. If someone tries to sell you spec-as-source for your CRUD app, push back.

Where does our team start?

For our adoption: start at spec-first for greenfield work and incremental spec-first for brownfield work. Move toward spec-anchored only on systems that already have stable contracts (APIs you publish, modules other teams depend on). Don't even consider spec-as-source until late 2026 at earliest.

4.The four-phase workflow

Every SDD tool you'll encounter — GitHub Spec Kit, Kiro, OpenSpec, Tessl — implements a variation of the same four phases. We'll use Spec Kit's vocabulary because it's the most widely adopted, and because the labs run on SPECTRA, which is built on top of Spec Kit. The commands and artifacts you'll see are therefore Spec Kit's — SPECTRA installs them for you and layers additional agents around them.

Phase 1 — Specify (“what”)

Output: a functional specification.

You answer: what should the software do? You describe behavior, requirements, acceptance criteria. You do not prescribe implementation details. This separation is the most important habit to build, and the one most engineers struggle with at first.

Spec Kit command: /speckit.specify. It produces a spec.md file with a structured template.

Phase 2 — Plan (“how”)

Output: a technical plan.

Given the functional spec, you describe the technical approach. Architecture, data model changes, interfaces, technology choices, non-functional requirements. Where the spec declares intent, the plan declares constraints on implementation.

Spec Kit command: /speckit.plan. It produces a plan.md (and often supplementary files like data-model.md).

Phase 3 — Tasks (“steps”)

Output: a discrete, ordered list of tasks.

The plan is broken into the smallest reasonable units of work. Each task is independently reviewable and testable. The list orders tasks so dependencies resolve.

Spec Kit command: /speckit.tasks. It produces a tasks.md file with checkboxes.

Phase 4 — Implement (and validate)

Output: working code, plus evidence that it meets the spec.

The agent runs each task, and after each one (or after a batch), you check: does the output match the spec? If yes, move on. If no, you have a choice — fix the code, or fix the spec. Whichever was wrong, you fix that one. The spec stays authoritative.

Spec Kit command: /speckit.implement. It runs through the task list with the AI agent.

A non-obvious property of the workflow

Each phase produces an artifact that constrains the next. That means each phase is also a review checkpoint. You don't review the final code in isolation — you review the spec when it's written, the plan when it's drafted, the tasks when they're enumerated, and the code when it's generated. By the time you're staring at a PR, divergence has already had four chances to be caught.

When a team complains that “AI-generated code is hard to review,” it's usually because they skipped phases 1–3 and tried to review only the output. Spec Kit's whole structure exists to spread the review load.

5.How SDD relates to things you already know

TDD

A unit test is a micro-spec. You write the test first, declaring what the function should do; then you write the function. SDD extends the same “specify before you build” thinking up to feature, system, and architectural scope.

Use both. TDD at the unit level, SDD at the feature/system level. They don't compete.

BDD

Behavior-driven development is the most direct ancestor of modern SDD. Gherkin scenarios — Given / When / Then — are literally executable specs. Cucumber and SpecFlow have been turning them into automated tests for over a decade.

What changed: AI agents can now generate code from those scenarios, not just verify against them. This is why people like Bryan Finster (who has been doing BDD for years) call SDD “BDD with branding.” He's not entirely wrong.

If your team already runs BDD, SDD is the smallest possible step from where you are. You're already most of the way there.

PRDs and design docs

These are advisory. Humans read them and write code that hopefully matches. Drift is normal and expected; nobody is alarmed when a 6-month-old design doc no longer matches the code, because nothing in the system enforces alignment.

SDD specs are enforced. The build fails when they don't match the code.

This is the cultural shift the team has to internalize: documents that nobody enforces become decoration. Documents that the build enforces become contracts.

Agile / Scrum

User stories with acceptance criteria are specs. The Definition of Done is a form of spec. You're already specifying things. SDD asks you to do that with more discipline and to make the specs authoritative rather than advisory.

You don't need to change your sprint structure to adopt SDD. You change what counts as “done” for a story and what artifacts get versioned.

6.When not to use SDD

There are tasks where spec ceremony costs more than it saves. The honest list, drawn from Augment's “skip the spec” criteria:

Skip the spec when……because
The work is exploratory or experimentalYou don't know what you want yet; specifying prematurely will lock in the wrong shape
A single prompt produces usable outputSpec overhead would exceed the work itself
The output can be reviewed in under five minutesYou can verify by reading; you don't need a contract
You're building a throwaway prototypeMaintenance benefits don't apply
The change is mechanical or low-riskBumping a version number doesn't need a spec

The trigger heuristic that's worth memorizing:

If you'd be annoyed to have the agent interpret requirements differently than you meant, write the spec. If you could fix the output in a quick follow-up prompt, skip it.

This is calibrated by stakes, not by intrinsic complexity. A two-line auth token check might warrant a spec because misinterpretation has security consequences. A 200-line refactor of a private function might not, because if the AI misreads, you'll catch it on diff review.

7.The honest case against (and why we're doing it anyway)

Spec-driven development has serious critics, and you should hear them before adopting any practice. This is the part most vendor blog posts skip.

Birgitta Böckeler (Thoughtworks): “Verschlimmbesserung”

Böckeler used Spec Kit, Kiro, and Tessl on real problems and found that current SDD tools generate too many files for the size of the problem they solve. Applied to a small bug fix, Spec Kit produced 4 user stories and 16 acceptance criteria when one prompt would have been better. She uses the German word Verschlimmbesserung — “an improvement that makes things worse” — for SDD setups that generate more markdown than code.

Her concrete warning: reviewing markdown can be harder than reviewing code. If your specs are repetitive, contain code-like detail, or duplicate what the code already says, you've made your job harder, not easier.

Take this seriously. We'll cover countermeasures in Module 5 (Best Practices and Pitfalls).

Bryan Finster: “BDD with branding”

Finster's argument is that the core insight of SDD — write specs first, derive code from them — has been agile/BDD wisdom for two decades. Calling it a paradigm shift in 2026 is marketing.

He's right that the insight isn't new. What's new is:

  1. AI agents are now competent consumers of specs, not just humans.
  2. CI/CD has matured to the point where spec enforcement is routine, not exotic.
  3. Tooling for spec authoring and validation is finally good enough to be worth adopting.

Together, those three changes make spec-first practice more powerful and more enforceable than ever before. So the practice is more valuable now than it used to be, even if the idea has been around for years.

The honest position: SDD isn't revolutionary, but it's currently the most practical way to keep AI-generated code aligned with intent in a production codebase.

Why we're adopting it anyway

Three reasons, in order of importance:

  1. It addresses a real problem. When AI agents generate code, the gap between “what we wanted” and “what we got” widens unless something keeps both ends explicit. Specs are that something.
  2. It scales review better than PR-time inspection. The Agoda study (10,000+ devs, March 2026) found that high-AI-adoption teams completed 21% more tasks but PR review time grew 91%. Pushing validation upstream into specs is one of the few ways to stop that bottleneck from breaking the team.
  3. It improves cross-functional collaboration. Done well, specs become the shared interface between PM, architecture, engineering, and QA. Done badly, they're just more documentation. Modules 6 and 7 are about making sure we land on “done well.”

8.The mental shift to make

Engineers tend to enter SDD thinking it's a tooling change: install SPECTRA, learn four slash commands, done. That's the version that produces Verschlimmbesserung.

The mental shift that actually unlocks the value:

  • Before: Code is the source of truth. Documents describe code.
  • After: Specifications are the source of truth. Code implements specs.

In the “before” view, drift is inevitable and you accept it. In the “after” view, drift is a build failure and you fix it.

You don't need to fully internalize this on day one. You'll get there by doing the labs. But notice when you're slipping back into “the code is the truth, the spec is documentation” thinking — that's the failure mode that turns SDD into bureaucracy.

Knowledge check

Spend 10–15 minutes on these. Click an answer to see whether you got it right and why.

Knowledge check 7 questions
Q1. A teammate asks the AI agent to “build a notification system.” The agent ships something that emails users on every database update, including system-internal changes. Which element of a “good spec” is most clearly missing from the original request?
Answer: c — Scope boundaries
“Build a notification system” has implicit outcomes (people get notified) and you could argue verification criteria (does it work?), but the core failure was no out-of-scope statement: nothing told the agent that system-internal changes should not trigger user emails. Out-of-scope lists are at least as important as in-scope.
Q2. Which of the following best describes the difference between a PRD and an SDD spec?
Answer: c — SDD specs are enforced
Length, location, and authorship are surface differences. The defining property is enforceability: an SDD spec is consumed by tooling that will fail the build if reality diverges.
Q3. Your team has a 25-line bug fix to make in a payment service. The bug is well-understood, the change is mechanical, and you can verify correctness from the diff in two minutes. Should you write a SPECTRA spec for it?
Answer: b — No
This is exactly the case Augment's “skip the spec” heuristic targets. Mechanical, well-understood, quickly reviewable work doesn't justify ceremony. Forcing a spec here is how SDD becomes bureaucracy.
Q4a. Match: Spec-first → which use case?
Answer: A
Spec-first is the lightest commitment — ideal for new feature development where the spec's value is up-front clarity rather than long-term maintenance.
Q4b. Match: Spec-anchored → which use case?
Answer: C
Spec-anchored shines on long-lived production systems with stable contracts — CI gates keep spec and implementation aligned over time.
Q4c. Match: Spec-as-source → which use case?
Answer: B
Spec-as-source works only with certified codegen toolchains where humans never edit the generated code — automotive ISO 26262 control software via Simulink is the canonical example.
Q5. Read this snippet from a teammate's spec for a file-upload feature:
“Create a function called uploadFile(file) that calls multer.single('file'), then writes to S3 using putObject(), then inserts a row into the uploads table with columns id, path, created_at.”
What's wrong with it?
It's prescribing implementation, not describing behavior. Function names, library calls, and database column names belong in the plan (Phase 2), not the spec (Phase 1). A behavior-level rewrite would be: “Users can upload files up to X MB; uploaded files are persisted in object storage and tracked in the application's database with timestamps; users can later list their own uploads.” Implementation choices come later, when the team picks tools and writes the plan.
Q6. True or false: If your SDD setup is producing more markdown to review than code, you've made the team's job harder, not easier.
Answer: True
This is Böckeler's Verschlimmbesserung observation. If specs are bigger than code, repetitive, or contain code-shaped detail, you've added overhead without adding value. Specs should be smaller and more abstract than the code they direct.
Q7. Why does the four-phase workflow (Specify → Plan → Tasks → Implement) reduce review burden compared to reviewing AI-generated code at PR time?
Each phase produces an artifact that's reviewed before the next phase begins. Divergence between intent and code can be caught at four checkpoints (spec, plan, tasks, implementation) instead of one (PR review). When everything piles up at PR review, reviewers either skim or burn out — both bad. Pushing review upstream into smaller, more focused artifacts spreads the cognitive load.
