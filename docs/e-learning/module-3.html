Module 3

Greenfield Lab — SPECTRA from Scratch

Install SPECTRA, walk through the four-phase workflow on a small to-do app, and feel the workflow in your hands before applying it to a real codebase.

Time 90 min
Format Hands-on lab
Prerequisites Modules 1, 2; an AI agent; Node 18+; uv & Git

Learning objectives

By the end of this module, you will be able to:

  1. Install SPECTRA and initialize a new project with a chosen AI agent.
  2. Walk through the four-phase workflow (/speckit.specify → /speckit.plan → /speckit.tasks → /speckit.implement) end to end on a small greenfield feature.
  3. Identify the artifacts produced at each phase and review them critically.
  4. Recognize when the agent is making assumptions you should have specified explicitly.

What you'll build

A simple single-page to-do web app. Users can add tasks, see them listed, mark them done (and undo), and delete them. Tasks persist in the browser via localStorage — no database, no backend.

Tech stack:

  • Next.js 14 (App Router) for the framework
  • React 18 with TypeScript
  • Tailwind CSS for styling
  • localStorage for persistence

This is small enough to finish in 90 minutes, but real enough to require thinking about edge cases. It's also a useful mirror for Module 4: when you start the brownfield lab, you'll be working with a starter app that looks structurally similar to what you build here. Same stack; different starting point.

A note on Git.This lab deliberately skips Git. Everything stays local on disk. You'll see the four-phase artifacts as files in your project, not as commits. In real work, committing at each phase boundary is a useful habit (covered in Module 5) — but for a 90-minute lab, the ceremony gets in the way of feeling the workflow.

1.Setup (15 minutes)

1.1 Pick your AI agent

SPECTRA works with every agent Spec Kit supports. Pick whichever you have access to:

  • Claude Code (recommended for this lab — strongest spec-writing performance)
  • GitHub Copilot (in VS Code)
  • Cursor
  • Gemini CLI

If your team has mixed adoption, this is a good moment to pair up — one person drives, one observes.

1.2 Scaffold the Next.js project

Use the official create-next-app to scaffold. From a directory of your choice:

npx create-next-app@14 todo-app --typescript --tailwind --app --no-src-dir --no-eslint --import-alias "@/*"
cd todo-app

When prompted by older versions of the CLI, accept the defaults (App Router, Tailwind, TypeScript, no src/ directory). The flags above pre-answer those prompts.

Verify the scaffold:

npm run dev

Open http://localhost:3000. You should see the default Next.js welcome page. Stop the dev server with Ctrl+C when you've confirmed it works.

1.3 Install SPECTRA

SPECTRA ships as a uv tool. Install it once, from anywhere — there's no repository to clone.

uv tool install spectra-cli --from git+https://github.com/xavient/spectra

Verify:

spectra

The banner prints a cli vX.Y.Z line — that's your installed version. Running spectra bare is informational only and never touches the current folder.

Don't have uv yet?On macOS or Linux run curl -LsSf https://astral.sh/uv/install.sh | sh; on Windows (PowerShell) run irm https://astral.sh/uv/install.ps1 | iex. Open a new terminal afterwards so uv is on your PATH. You also need Git, which uv uses to fetch SPECTRA. Step-by-step instructions for all three operating systems are on the SPECTRA install page.
What you just installed.spectra is a setup and lifecycle command, not a replacement for Spec Kit. In the next step it will install Spec Kit's specify CLI for you if you don't already have it — the four-phase workflow you're about to run is Spec Kit's, and SPECTRA is what puts it in place and adds agents on top.

1.4 Install SPECTRA into the scaffolded project

From the todo-app/ directory:

spectra install

That one command does the whole setup: it installs Spec Kit's specify CLI if it's missing, offers to run specify init because this folder isn't a Spec Kit project yet, registers the public SPECTRA catalog, and installs SPECTRA's agents. When it asks which AI agent you're using, pick the one you chose in 1.1.

After it finishes, your directory will contain (in addition to the Next.js scaffold):

.specify/                # Spec Kit's state, plus the SPECTRA catalog
memory/
→ constitution.md      # Project-wide context (initially a template)
.claude/                 # Or .github/, .cursor/, etc., depending on agent
Restart your AI agent.Commands are written to disk at install time, so an agent that was already running won't see them. Restart it before the next step.

The four-phase slash commands (/speckit.specify, /speckit.plan, /speckit.tasks, /speckit.implement) are now available inside your AI agent's chat interface for this directory — along with SPECTRA's own speckit.spectra.* agents. Run spectra agent-list to see those; they go beyond the four phases and are outside the scope of this lab, but they're worth knowing exist.

The trigger form differs by agent.Spec Kit translates each command into your agent's native format at install time, so what you actually type depends on your agent. Claude registers them as skills invoked with dashes — /speckit-specify, /speckit-plan, and so on. Other agents keep the dots — kiro-cli uses /speckit.specify. This course writes the dotted form throughout; swap in dashes if you're on Claude. Your agent's own command or skill list shows the exact trigger.

1.5 Sanity-check the agent

Open your AI agent in this directory and try a no-op:

/speckit.specify

You should see a prompt asking what feature you want to specify. If you see that, setup is done. If you don't, the agent isn't seeing the slash commands — most often a fixable matter of restarting the agent or pointing it at the right directory.

2.Author the Constitution (10 minutes)

The Constitution holds project-wide context that doesn't belong in any single spec. Open memory/constitution.md. It starts as a template; replace it with the following.

Note.Some Spec Kit versions auto-generate a richer Constitution template. If yours has more sections than this, that's fine — the content below is the minimum for this lab. Keep what's there if it helps, but don't add ceremony for ceremony's sake.
# Todo app — Constitution

## Stack
- Next.js 14 (App Router) with TypeScript
- React 18
- Tailwind CSS for styling
- localStorage for persistence — no backend, no database, no API routes

## Code organisation
- Page lives in `app/page.tsx`
- Components live in `app/components/`
- Storage helpers and shared types live in `lib/storage.ts`
- Components that use browser APIs (localStorage, useState, useEffect)
  declare `"use client"` at the top

## Styling conventions
- Tailwind utility classes only — no separate CSS files for layout
- `app/globals.css` contains only the three Tailwind directives
- Default Tailwind palette; no custom theme extension for this lab

## Data conventions
- Todos are objects: `{ id: string, text: string, completed: boolean, createdAt: string }`
- `createdAt` is an ISO 8601 string
- IDs are generated using `crypto.randomUUID()` (collision-safe; available in
  all modern browsers)
- The localStorage key is exposed as a single named constant in `lib/storage.ts`,
  not duplicated as a magic string

## UI conventions
- Single page, no routing
- Empty state when there are no tasks
- Newest task at the top of the list
- Completed tasks show a strikethrough; the row is not removed

This is short on purpose. The Constitution should hold durable conventions, not the world. If something here turns out to be wrong later, you'll change it once and every future spec inherits the change.

Why are some specifics here?You'll notice the Constitution names crypto.randomUUID() and a single named constant for the storage key. These aren't ceremony for its own sake — they're decisions worth pinning at the project level so the agent doesn't reinvent them in every spec. Compare the brownfield lab in Module 4, where the starter codebase doesn't follow either of these and you'll see why having them in the Constitution matters.

3./speckit.specify (15 minutes)

In your AI agent, run:

/speckit.specify

Build a single-page to-do web app. The user can add a task, see all
tasks in a list, mark a task as done (and undo), and delete a task.
Tasks persist across page reloads via localStorage. The home page
("/") is the only page. Newest tasks appear at the top.

The agent will produce a draft spec at specs/<NNN>-todo-app/spec.md (or similar — the path varies slightly by Spec Kit version). It will likely ask clarifying questions, or include [NEEDS CLARIFICATION] markers in the draft. Engage with these — the dialogue is part of the practice, not a flaw.

3.1 Review checklist

Once the agent produces a draft, don't accept it as-is. Open the file and check it against the six-element framework from Module 2:

  • Outcomes are observable (someone can tell whether the work is done by using the app)
  • In-scope items are listed
  • Out-of-scope items are listed (this is the one most often missing)
  • Constraints are stated (or covered by the Constitution and not repeated here)
  • Decisions made — empty input handling, ordering, completed-task display
  • Verification criteria — concrete, runnable checks, not vibes

If any of these are weak, edit the spec directly. You can also re-prompt the agent: “The out-of-scope list is missing — please add at least four items based on what the Constitution and the request imply.”

3.2 Things to deliberately decide

These are the questions a thin spec will leave unanswered. You should make explicit decisions:

  • Empty input. What happens when a user presses “Add” with an empty string? With only whitespace? Reject silently, show an error, disable the button?
  • Sorting and ordering. Newest at the top, but what about completed tasks — do they stay in place, sink to the bottom, or hide?
  • Editing existing tasks. In or out of scope? (For this lab, recommend out of scope — it's a Module 4 brownfield exercise candidate.)
  • Maximum length. Should there be a character limit on task text?
  • Confirmation on delete. Hard delete with no confirmation, or a “Are you sure?” step? (For 90 minutes, recommend hard delete with no confirmation.)
  • localStorage failures. What if the browser is in private mode and writes throw? Crash, ignore silently, or show a toast?

You won't get all of these perfect. The point is to notice that you're making decisions, not letting the agent silently make them for you.

3.3 Stop when

You stop iterating on the spec when a new engineer could implement the app from your spec without asking you anything. Not before. If you'd still need to clarify something to write the code, the spec isn't done.

4./speckit.plan (15 minutes)

In your agent:

/speckit.plan

The agent generates a plan.md (and possibly supporting files) describing how to build what the spec describes. This is where you make implementation decisions: file layout, component structure, what state lives where, how localStorage is read and written.

4.1 Review checklist for the plan

The plan should:

  • Identify the components to create — minimum: a form, a list, and a list-item component
  • State where state lives (the page, lifted up; not scattered across components)
  • Describe the localStorage read/write pattern (load once on mount; save on change; handle the SSR case where window is undefined)
  • Decide which fields exist on a Todo object and where the type is defined
  • Match the Constitution's conventions (file layout, crypto.randomUUID(), single storage-key constant)

4.2 What the plan should not contain

  • Full component bodies (that's /speckit.implement's job)
  • Specifics that contradict the Constitution (if it does, fix one or the other — both being authoritative is the point of having both)
  • Things that should have been in the spec (“we should also support tags” — no, that's a scope change, go back to /speckit.specify)

If the plan is wrong, fix it before moving on. The cost of a wrong plan caught here is minutes. The cost of a wrong plan caught at /speckit.implement is potentially the whole afternoon.

4.3 SSR / hydration: the one gotcha to watch for

Next.js renders pages on the server first, then hydrates them in the browser. localStorage doesn't exist on the server. If the plan reads localStorage during the initial render, the client and server will produce different HTML and React will throw a hydration warning.

The right pattern: the page renders an empty initial state on first paint, then a useEffect hook reads localStorage after mount and updates state. The plan should call this out explicitly. If it doesn't, push back: “How does this avoid hydration mismatch when localStorage is read?”

This is the kind of stack-specific issue the Constitution can't anticipate but the plan must.

5./speckit.tasks (10 minutes)

/speckit.tasks

The agent breaks the plan into a list of discrete, ordered tasks in tasks.md. Each task should be small enough to implement and verify on its own.

5.1 Review checklist

  • Tasks are roughly the right size — neither “build the app” (too big) nor “import useState” (too small)
  • Tasks are ordered so dependencies resolve naturally (storage helpers and types before components; form before list; list before delete)
  • Each task has a clear “done” criterion you could check off without ambiguity
  • The hydration handling is its own task or explicitly part of the page-component task

5.2 Common defects

  • Mega-task syndrome — “Build the page” with no breakdown. Push back: split into state setup, render, mount-effect for load, change-effect for save.
  • Missing wiring — components listed but no task to connect them on the page. Add it.
  • No verification step — the last task should be “manually verify against spec criteria” or similar. If it's missing, add it.

6./speckit.implement (20 minutes)

/speckit.implement

The agent works through the task list, generating code for each task. Depending on your agent, it may:

  • Stop after each task and ask for confirmation (Claude Code default)
  • Run through the whole list and report at the end (some Cursor configurations)
  • Pause when it hits ambiguity (most agents)

6.1 Watch for these moments

  • The agent invents a new requirement. If it suddenly adds a “due date” field that wasn't in the spec, stop it. Either the spec was wrong (go back and fix it) or the agent is hallucinating scope. (Note: if you find yourself wanting due dates, don't add them here — that's the Module 4 brownfield exercise.)
  • The agent uses Date.now() for IDs. The Constitution specified crypto.randomUUID(). If the agent ignores it, push back. This is exactly the kind of small Constitution violation that becomes cruft over time if uncaught.
  • The agent hardcodes the localStorage key. Same logic — the Constitution specified a single named constant. If the agent inlines "todos" strings, push back.
  • The agent skips the hydration consideration. If you see localStorage being read in a component body (not inside a useEffect), the build will warn. Have the agent fix it.

6.2 Run the app

Once /speckit.implement finishes:

npm run dev

Open http://localhost:3000. Try:

  1. Add a task. Does it appear at the top of the list?
  2. Mark it done. Does the strikethrough appear?
  3. Mark it undone. Does the strikethrough disappear?
  4. Delete it. Does it vanish from the list?
  5. Add three tasks, refresh the page. Are all three still there?
  6. Open the browser devtools → Application → Local Storage. Is there a key matching the constant from your Constitution? Does its value look like a JSON array of todo objects?

If any of these fail, you have a divergence between spec and code. Investigate:

  • Is the spec wrong? (Did you not specify what you actually wanted?)
  • Is the code wrong? (Did the agent miss something the spec stated?)

Whichever is wrong, fix that one. Then re-verify.

7.Reflection (10 minutes)

Spend 10 minutes writing answers to these in a REFLECTION.md file in your project root. You don't need to share these with anyone, but writing them down is the difference between learning the practice and just executing the steps.

  1. Where did you make decisions during /speckit.specify that the agent would have made wrongly if you'd left them implicit?
  2. What got caught at /speckit.plan review that would have been more painful to fix at /speckit.implement? (The hydration handling is the obvious candidate — was there anything else?)
  3. Did the agent ever invent scope? How did you notice?
  4. How does this feel compared to “just write a prompt and let the agent code”? Faster? Slower? Different in kind?
  5. Of the conventions in your Constitution, which ones did the agent honor without prompting, and which did you have to reinforce?

There's no right answer to any of these. The honest one is the useful one.

8.Common issues and how to handle them

“The agent's spec is way too long”

Edit it down. Spec Kit's default templates can be verbose, and some agents pad them further. Anything that doesn't add information should go. The good test from Module 2 still applies: if a sentence wouldn't change the agent's behavior, it doesn't belong.

“The agent ignored my Constitution”

Some agents have weaker context discipline than others. If the Constitution says crypto.randomUUID() and the agent uses Date.now() anyway, two things to try:

  1. Reference the Constitution explicitly in the spec or plan: “Per the Constitution, IDs use crypto.randomUUID().”
  2. Re-prompt mid-implement: “The Constitution requires crypto.randomUUID() for IDs. Replace the Date.now() calls.”

If your agent consistently ignores Constitutions, that's a tooling-level concern worth raising on your team.

“The phases blur into each other”

Especially common with Claude Code, which can helpfully (or annoyingly, depending on context) do all four phases in one pass when you give it a sufficiently specific request. To prevent this, run the slash commands one at a time and review the artifact between each. The whole point of the workflow is the review checkpoints.

“I want to skip /speckit.tasks”

You can. Some teams find /speckit.specify + /speckit.plan + direct implementation works fine for small features. The argument for keeping /speckit.tasks is that it forces explicit task-sizing decisions. The argument against is overhead.

For this lab, do all four. After the lab, decide for your team.

“The hydration warning won't go away”

The classic causes:

  • localStorage being read during render rather than inside a useEffect.
  • The initial state of useState differing between server and client.
  • A component that uses Date.now() or Math.random() during render (different value on server vs client).

The fix in all three cases is the same: render a stable initial state on the server, then update once mounted. The Spec Kit plan should have called this out — if it didn't, that's a useful note for your reflection.

What you should now know

  • Spec Kit's four phases produce four reviewable artifacts (spec.md, plan.md, tasks.md, working code) with explicit review checkpoints between each.
  • The Constitution holds durable conventions; the spec holds task-specific intent. Keeping them separate keeps both readable.
  • Each phase forces a different kind of decision — what (specify), how (plan), steps (tasks), code (implement). Mixing them produces vague specs, kitchen-sink plans, or untested code.
  • Stack-specific gotchas (like Next.js hydration) belong in the plan, not the Constitution. The Constitution is for durable team conventions; the plan is for how-this-feature-works-on-this-stack.
