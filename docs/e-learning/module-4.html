Brownfield Lab — Add “Due Date” to the To-Do App

Apply SPECTRA to an existing codebase using the incremental-spec pattern. Author a Constitution by reading code, distinguish convention from cruft, and spec only the area of change — never the whole system.

Time 2–3 hours
Format Hands-on lab
Prerequisites Modules 1–3; SPECTRA installed
★
Lab codebase — lab-codebase.zip
A minimal but fully-working Next.js + TypeScript + Tailwind to-do app with no specs and no due-date feature. About 200 lines across five files.
Download

Learning objectives

By the end of this module, you will be able to:

  1. Apply the brownfield SDD pattern (incremental specification at the area of change) to a real codebase.
  2. Author a Spec Kit Constitution by reading existing code, not by writing it from scratch.
  3. Distinguish conventions (patterns to preserve) from cruft (rough edges that aren't deliberate).
  4. Write a focused spec for a small feature without trying to spec the entire system.
  5. Recognize and handle the friction Spec Kit has on brownfield work, including the issue #1191 limitation.
  6. Decide, during validation, whether to fix the code or fix the spec.

Why this lab is the centerpiece

Greenfield SDD is the easy case. Tutorials and demo videos almost always show greenfield. Most real engineering work is brownfield — you have a codebase, it has conventions (some good, some weird), and you need to add a feature without breaking the rest of it.

The brownfield case is where most teams either give up on SDD because the tools “don't fit,” or generate giant codebase-summary specs that nobody reviews. There's a third path, which this lab teaches: spec only the area of change.

If you only do one lab in this course, do this one.

1.Run the starter app (15 min)

1.1 Get the lab codebase

Download lab-codebase.zip using the link above (or ask the course owner for it). Unzip somewhere you can work in:

unzip lab-codebase.zip -d ~/sdd-brownfield-lab
cd ~/sdd-brownfield-lab/lab-codebase

1.2 Install dependencies and run

You need Node.js 18 or newer.

npm install
npm run dev

Open http://localhost:3000. You should see “My To-Dos” — an input box, an “Add” button, and (after you add some) a list of tasks. Try it out:

  1. Add a few tasks.
  2. Mark some done. Notice the strikethrough.
  3. Refresh the page. Tasks should persist.
  4. Delete a task.

When you're satisfied it works, stop the dev server with Ctrl+C.

1.3 Read the code

Spend 10 minutes reading the source. Don't skim. The whole codebase is about 200 lines across:

  • lib/storage.ts — Todo type and localStorage helpers
  • app/page.tsx — the main page; owns the state and effects
  • app/components/TodoForm.tsx — input + Add button
  • app/components/TodoList.tsx — list rendering and empty state
  • app/components/TodoItem.tsx — single task row

While you read, keep a small note open and write down what you see. Specifically:

  • Things that look like conventions — consistent patterns, deliberately chosen, you'd want to preserve.
  • Things that look like cruft — rough edges, probably not deliberate, you'd fix in passing.

This list is the heart of the brownfield work. Your Constitution will encode the conventions. The cruft you'll either tolerate (out of scope), fix during the work (in scope), or note for later (a follow-up spec). But you have to decide, which means you have to name them first.

A hint, not a spoiler. The codebase is small but it does have at least three pieces of intentional cruft. If you find none, you're skimming. If you “find” ten, you may be classifying conventions as cruft. The right number is small.

2.Install SPECTRA on the brownfield repo (10 min)

Now the brownfield friction starts. Spec Kit was designed greenfield-first, so initializing it on an existing repo requires care.

2.1 Initialize

spectra install

Same command as Module 3. When prompted for an AI agent, pick the same one you used there, and restart the agent afterwards so it picks up the commands.

This creates .specify/, memory/constitution.md, and the agent config directory. Verify your existing files (app/, lib/, package.json, etc.) are untouched — nothing in the setup rewrites your source.

2.2 The known limitation

A heads-up that's worth internalizing now rather than discovering at a bad moment:

Spec Kit issue #1191: Spec Kit is optimized for net-new feature creation. Updating an existing spec — for instance, when reviewing a feature in production and wanting to amend the spec to reflect a small change — is awkward, and the workflow assumes “feature = new spec folder.”

Source: github.com/github/spec-kit/issues/1191 (referenced in Augment's SDD guide).

For this lab, we sidestep the issue by treating the due-date addition as a new feature spec rather than an amendment to a (non-existent) original to-do spec. That's the right call here. In your own brownfield work, plan around this — each meaningful change becomes its own small spec.

3.Author the Constitution from existing code (25 min)

In a greenfield project, you write the Constitution before the code. In a brownfield project, the code exists first — so you read it and extract the Constitution from observed patterns. This is the most distinctive brownfield activity, and the one most likely to go wrong if rushed.

3.1 Use your AI agent to help, but don't blindly trust it

Open memory/constitution.md. It's a starter template; you'll replace it.

The temptation is to ask your agent: “Read this codebase and generate a Constitution.” Don't do that, or at least don't only do that. Two reasons:

  1. The agent will pick up cruft as convention. It can't tell which patterns are deliberate and which are accidental.
  2. The Constitution it produces will be too long. Agents over-include “just in case.” A bloated Constitution is the markdown-monster failure mode from Module 1.

The right approach: have the agent draft, you edit ruthlessly. Or write it yourself referencing the code. Either way, the human makes the calls.

3.2 Draft

Try this prompt with your agent:

Read the existing codebase (app/page.tsx, app/components/*, lib/storage.ts).
Identify patterns that are repeated and look deliberate — file layout,
component conventions, styling choices, data shapes, dependency choices.
Draft a brief Constitution capturing only those patterns. Skip anything
that appears in only one place. Aim for under 30 lines.

The agent will produce something. Read it carefully. Now edit.

3.3 What to keep, what to cut

Try writing your own version first, before peeking. Then compare.

# Todo app — Constitution

## Stack
- Next.js 14 (App Router) with TypeScript
- React 18
- Tailwind CSS for styling
- localStorage for persistence — no backend, no API routes

## Code organisation
- Page lives in `app/page.tsx`; it owns state and passes handlers down
- Reusable components live in `app/components/`
- Types and storage helpers live in `lib/storage.ts`
- Components using browser APIs declare `"use client"` at the top

## Styling conventions
- Tailwind utility classes only — no separate CSS files for layout
- `app/globals.css` is just the three Tailwind directives
- Default Tailwind palette; no custom theme extension yet

## Data conventions
- Todos shape: { id: string, text: string, completed: boolean, createdAt: string }
- `createdAt` is an ISO 8601 string
- Newest tasks render at the top of the list
- Completed tasks remain in the list with strikethrough; they are not removed
- Empty input is rejected silently (no error message); no toasts

## State conventions
- Page owns state; components are presentational and receive callbacks as props
- localStorage is read once on mount inside a `useEffect`; written on every change
  inside a separate `useEffect`. This is required to avoid hydration mismatch.

## Known cruft (NOT conventions — fix when convenient)
- Magic string "todos" repeated in `lib/storage.ts` — extract a constant
- Leftover `console.log` in the page's mount effect — remove
- IDs generated with `Date.now().toString()` — switch to `crypto.randomUUID()`
  (collision-safe; available in all modern browsers)

Notice what's happening in that last section. The Constitution explicitly names the cruft as cruft, separate from conventions. This serves two purposes:

  1. It prevents the agent from preserving cruft as if it were intentional. Without this section, an agent reading “the code uses Date.now() for IDs” would happily continue using Date.now() for new IDs in the due-date feature.
  2. It creates a known list of follow-up work. The bonus exercise at the end of this module addresses one of these. The rest are stand-alone cleanup specs you (or your team) can pick up later.

This is more honest than the typical “ignore the cruft and hope” approach. Cruft you've named is cruft you can decide what to do with.

3.4 What if you found different cruft than the sample?

Good. If you found patterns you suspect are cruft but you're not sure, ask yourself:

  • Is this pattern repeated, or is it in one place? Repeated patterns are more likely conventions; one-off oddities are more likely cruft.
  • Is there an obvious cleaner alternative? If yes, it's probably cruft. If no, it might be a deliberate trade-off you don't yet understand.
  • Would a careful code reviewer catch this? If yes, cruft. If it would slip past, more likely a convention you just haven't internalized.

You don't have to be right. The point is to decide, then revise as you learn more. A Constitution is a living document.

4./speckit.specify — but only for the area of change (30 min)

This is where brownfield SDD diverges most from greenfield. You are not specifying the whole to-do app. You are specifying the due-date addition. The existing app is context, not subject.

4.1 Run /speckit.specify

/speckit.specify

Add a "due date" field to to-do items. The field is required when
creating a task: the user picks a date that must be in the future
(today is not allowed; tomorrow or later only). The due date displays
on each task in the list. If a task's due date is in the past and the
task is not yet completed, the due date displays in red. Existing
behaviour (add, mark done, delete, persistence) is preserved.
Build on the existing patterns documented in the Constitution.

The agent will produce a draft spec. The most common failure mode is that the agent over-scopes — it'll add things you didn't ask for, like sorting by due date, filtering by date range, recurring todos, reminder notifications, or “due soon” warning colours. Push back hard on each one.

4.2 Review the draft

Open the generated spec (specs/<NNN>-due-date/spec.md or similar) and apply the six-element checklist from Module 2. Some specific things to look for in this spec:

Outcomes — must be observable. Not “users can set due dates.” Closer to: “When creating a task, the user must pick a due date in the future. The due date is visible on each task in the list. Tasks whose due date has passed and that are not yet completed display the due date in red.”

In-scope — minimal, surgical. This feature adds a date field, validation that it's in the future, display of the date, and a red treatment when overdue. That's it.

Out-of-scope — write at least 5. This is the section that prevents an afternoon's feature from becoming a week. Suggested entries:

  • Editing the due date after creation
  • Sorting or filtering by due date
  • Recurring or repeating tasks
  • Notifications, reminders, or emails
  • Time-of-day component (date only, no time)
  • Time zones (local time only; cross-timezone is out)
  • “Due soon” warnings (orange, yellow, etc.) — only past-due is red
  • Optional due dates (the field is required for new tasks)

Constraints — reuse the Constitution, don't repeat it. Things like “Next.js + Tailwind + localStorage” are in the Constitution; the spec doesn't restate them. Spec-level constraints are things specific to this feature: e.g. “Due date is a date-only string in YYYY-MM-DD format” or “The date input uses <input type='date'> for browser-native date picking.”

Decisions already made. This is where you cut off rabbit holes. Examples:

  • Date format: ISO 8601 date-only (YYYY-MM-DD), no time component.
  • “In the future” is defined as: the picked date is strictly greater than today's date in the user's local timezone.
  • “Past due” is defined as: the due date is strictly less than today's local date AND the task is not completed.
  • Validation runs on submit; if invalid, the task is not added and a visible inline error appears next to the date input.
  • The red treatment is Tailwind's text-red-600. No icon, no badge, no animation.

Verification criteria. Write at least 6, with at least 2 edge cases.

  • Submitting a task with a due date of tomorrow succeeds and the task appears in the list with that date.
  • Submitting a task with today's date is rejected with an inline error; no task is added.
  • Submitting a task with a date in the past is rejected with an inline error; no task is added.
  • Submitting a task with no date set is rejected with an inline error; no task is added.
  • A task with a due date in the past and completed: false displays the due date in red.
  • A task with a due date in the past and completed: true does not display in red.
  • Edge: a task created today with tomorrow's due date displays in normal colour today, and would display in red two days from now (verify by adjusting system clock or using a far-past test date).
  • Edge: refreshing the browser preserves all due dates; existing tasks (created before this change, with no dueDate field) load without errors.

The pattern: each line is a single, runnable check. None of them say “works correctly” or “handles errors gracefully.” Each one would either pass or fail when you walk through it in the browser, with no interpretation needed.

4.3 The spec smell to watch for

If your spec mentions specific component file names, function signatures, or Tailwind class strings, you've drifted into the plan. Pull those out. The spec describes behavior; the plan describes implementation. The Module 2 worked example shows the difference if you need a refresher.

5./speckit.plan (20 min)

/speckit.plan

Now you make implementation decisions, anchored to the existing codebase.

5.1 What the plan should describe

  • Type change: extend Todo in lib/storage.ts to include dueDate: string (the ISO YYYY-MM-DD string).
  • Backward compatibility on load: existing tasks in localStorage have no dueDate field. The load path should either coerce them to a sentinel value or filter them out — pick one and decide deliberately. Recommendation: load them as-is with dueDate: undefined typed as optional, and treat undefined as “no due date, never overdue” — but mark that migration step out of scope or note it as cruft for later.
  • TodoForm changes: add an <input type="date"> next to the text input. Add local state for the picked date. Add validation logic that runs on submit. If invalid, set an error message in local state and render it; do not call the parent's onAdd.
  • Validation logic: “in the future” check using the YYYY-MM-DD string from the input compared against today's local date in the same format. Pure string comparison works correctly for ISO dates (lexicographic order = chronological order).
  • page.tsx changes: the addTodo function now accepts a dueDate parameter and stores it on the new todo. No other state changes.
  • TodoItem changes: display the due date next to the text. Compute “is overdue” using the same string-comparison technique. Apply text-red-600 to the date span when overdue and not completed.
  • No new dependencies. Native <input type="date"> and date-string comparison are sufficient.

5.2 Review the agent's plan

The agent will draft a plan that's roughly along these lines but probably with some divergence. Things to watch for:

  • Date object trap. If the agent writes validation as new Date(input) > new Date(), you have a hidden timezone bug — the input string parses as midnight UTC, and the comparison fails near midnight in some timezones. Push back: “Compare ISO date strings lexicographically using today.toISOString().split('T')[0] for the right-hand side.”
  • Wrong storage key. If the plan introduces a new localStorage key for due dates (“efficiency”), reject it. The Constitution implies one storage location for todos; a new key is scope creep.
  • Migration overreach. If the plan proposes rewriting all existing todos in localStorage to add a default dueDate value, push back. That's not necessary and it touches data the user didn't explicitly ask to modify. The simpler path: handle missing dueDate at the type level and at the render level.
  • Custom date pickers or libraries. Anything that introduces a new dependency (react-datepicker, date-fns, etc.) is overkill. Native <input type="date"> and string math are enough.

6./speckit.tasks (10 min)

/speckit.tasks

The agent breaks the plan into discrete tasks. A reasonable task list might look like:

  1. Extend the Todo type in lib/storage.ts to include an optional dueDate field.
  2. Update app/page.tsx's addTodo to accept and persist dueDate.
  3. Add a date input and local error state to TodoForm.
  4. Implement future-date validation in TodoForm's submit handler.
  5. Update TodoForm's onAdd callback signature to pass dueDate.
  6. Display the due date in TodoItem next to the text.
  7. Implement the “overdue” string comparison and apply text-red-600 when overdue and not completed.
  8. Manual verification against spec criteria.

That's about 8 tasks for an afternoon's work. If your agent produces 4 mega-tasks or 25 micro-tasks, ask it to re-decompose.

7./speckit.implement (45–60 min)

/speckit.implement

The longest phase. The agent works through tasks, generating code. Watch for the same pitfalls as in Module 3, plus brownfield-specific ones.

7.1 Brownfield-specific things to watch for

  • The agent ignores existing patterns. If the agent introduces a state-management library (Redux, Zustand) when the existing code uses plain useState, that's a regression. Stop it. State at the page level was a deliberate convention.
  • The agent rewrites things you didn't ask it to. Some agents will helpfully “fix” the cruft you named in the Constitution — replacing Date.now() IDs with crypto.randomUUID(), extracting the storage-key constant, removing the console.log. That's actually fine if you want it, but it's a scope decision: are you fixing cruft as part of this feature, or saving it for a follow-up? Decide deliberately. Mixing cruft cleanup into feature work makes PR review harder.
  • The agent adds new files when existing ones would do. A new dateUtils.ts module for one helper function is over-engineered. The function probably belongs in lib/storage.ts or inline in the component.
  • Date math gone wrong. Comparing new Date('2026-04-30') < new Date() in JavaScript has timezone subtleties. The agent will sometimes produce code that looks right but is off-by-one near midnight. The reliable pattern (worth pushing for explicitly): compare YYYY-MM-DD strings directly. Lexicographic comparison works correctly for ISO dates.
  • Hydration warnings. If the “today” date is computed during render rather than inside an effect or event handler, server and client may compute different values, triggering a React hydration warning. The cleanest pattern: compute “today” only inside the validation handler (event-time) and inside the TodoItem's useMemo or directly during client-side render after hydration is complete.

7.2 Run after meaningful tasks

Don't wait until the end. After tasks 1–5 (form + validation), restart the dev server and try:

  • Add a task with a date in the future. Should appear in the list with the date shown.
  • Try to add with today's date selected. Should show an inline error and not add.
  • Try to add with no date selected. Should show an inline error and not add.
  • Try to add with a past date. Should show an inline error.

After tasks 6–7 (display + red), pick a task you already have and manually edit its dueDate in the localStorage entry to a past date (browser devtools → Application → Local Storage → edit the JSON), then refresh. The date should now display in red. Mark the task done — the red should disappear.

7.3 If something doesn't work

You have two questions to ask, in order:

  1. Does the spec describe what you actually want? If you're surprised by the behavior, often the spec was vague. Update the spec, then re-implement just the affected task.
  2. Does the code implement the spec? If the spec is right but the code is wrong, fix the code (or have the agent fix it).

Don't fix code without checking the spec first. That's how spec-anchored repos drift back into being code-as-truth repos.

8.Validate against the spec (20 min)

This is the part most teams skip. Don't.

8.1 Walk through the verification criteria

Open your spec's verification section. Go through each criterion and verify it holds. For UI criteria, walk through them in the browser. For edge cases, set up the precondition deliberately (edit localStorage, change system clock if you can, add tasks at the right times).

8.2 Spec-vs-implementation checklist

  • Existing tasks (created before this change, with no dueDate) still load without errors.
  • Adding a task with tomorrow's date succeeds.
  • Adding a task with today's date is rejected with a visible inline error.
  • Adding a task with a past date is rejected with a visible inline error.
  • Adding a task with no date is rejected with a visible inline error.
  • The due date appears on every task in the list.
  • An overdue, uncompleted task displays its due date in red.
  • Marking the overdue task complete removes the red treatment.
  • Refreshing the browser preserves due dates.
  • No regressions: add (with valid date), mark done, delete still all work.

8.3 What if there's a gap?

If you find a behavior not covered by your verification criteria, add the criterion to the spec, then verify. The spec is a living artifact. If you found something the spec missed, future you (or a teammate) would have missed it too. Strengthening the spec strengthens the harness.

If you find a bug, classify it (this is the SpecOps loop from Module 1):

  • Spec-to-implementation gap — spec was clear, code diverged. Fix the code, and consider whether your validation gates should have caught it earlier.
  • Intent-to-spec gap — spec was incomplete. Fix the spec first, then the code.

Each classification points to a different improvement. Spec-to-implementation gaps mean your testing/validation is too loose. Intent-to-spec gaps mean your spec-writing process is missing something. Both are useful signals.

9.Reflection (15 min)

Same format as Module 3 — write REFLECTION.md answers honestly, don't share unless you want to.

  1. The Constitution-from-existing-code activity — was it harder or easier than you expected? What did you almost include that you decided to leave out?
  2. The cruft list — did you find the three pieces planted in the codebase? Did you find others that turned out to be conventions on closer inspection?
  3. How tempted were you to spec the entire app? How did you push back against that temptation?
  4. The agent's first-draft spec — what did it over-include? What did it miss?
  5. The first time during /speckit.implement that you had to choose between “fix the code” and “fix the spec” — what was the situation, and which did you pick? Why?
  6. What would have happened to this feature if you'd skipped the spec entirely and just told the agent “add a due date field”? What problems would you have caught at code review instead of spec review?
  7. What's the smallest change to your team's current workflow that would let you do this kind of brownfield SDD on a real Jira ticket next week?

The last one is the most important. SDD is only worth learning if it changes what you do at work. Question 7 is what we'll come back to in Module 7.

10.Bonus exercise (optional, 30 min)

If you finished early and want to push deeper:

Pick one piece of cruft from the codebase (the magic "todos" string, the leftover console.log, or the Date.now() ID generation) and write a small spec to fix it. Use the same workflow. The point: cruft fixes are usually pure scope-creep candidates during feature work, but they become tractable when you spec them as their own focused changes.

Recommendation: start with Date.now() → crypto.randomUUID(). It has the most concrete benefit (collision safety) and forces you to think about whether existing IDs in localStorage need migration. (Spoiler: they don't, because IDs are opaque strings — you just want new IDs to use the new generator.)

This is the brownfield convergence pattern from Module 1: each change adds a small spec, frequently-touched areas accumulate spec coverage, and over time the codebase starts behaving more like a greenfield project. Not because you specced the whole thing — because you specced each change.

What you should now know

  • Brownfield SDD is incremental, not comprehensive. You spec the change, not the system.
  • The Constitution is extracted from existing code, not imposed on it. Distinguishing convention from cruft is the actual skill.
  • Naming cruft explicitly in the Constitution (separately from conventions) prevents agents from preserving it as if it were intentional.
  • Spec Kit's greenfield bias creates real friction on existing repos (issue #1191 is one example). The workaround is to treat each change as a new feature spec and not try to maintain a single evolving “main spec.”
  • The validation phase is non-optional. Skipping it turns SDD back into vibe coding with extra ceremony.
  • Bug classification (spec-to-impl gap vs. intent-to-spec gap) drives different improvements — to validation gates versus to elicitation patterns. Use both.
