# Review body

<!--
  HOW TO USE THIS TEMPLATE
  - This is the structure `speckit.spectra.review-pr` fills when it publishes a review. It defines
    TWO shapes: the summary body, and the individual inline comment. Both are below.
  - Fill every section that has accepted findings. Sections with none are removed entirely —
    an empty "## Blockers" heading reads as a finding you forgot to write.
  - Guidance in HTML comments does not render on GitHub, but it MUST still be deleted, along
    with every [PLACEHOLDER] token.
  - The heading above is a label for this file, not part of the published body. Do not post it.

  WHAT THIS TEMPLATE DOES *NOT* CONTROL — read this before overriding
  Three elements are emitted by the command itself and are not yours to move or remove:
    1. the `<!-- spectra:review-pr revision=… -->` anchor comment — a later run finds its own
       previous reviews by it, so `--since` delta re-review and self-review detection depend on it;
    2. the "AI-assisted, human-curated" disclosure line — a published review has to say what it is;
    3. the "Coverage and limits" section — it is what stops a review implying assurance it did not
       earn, so it cannot be configured away.
  Nor does this template decide *judgment*: the severity rubric and its floors, the confidence cap,
  the anchor rule, the selection grammar, and how the verdict is derived all stay in the command. If
  those were per-project, two reviews of the same diff would not agree, which is the one thing this
  command exists to prevent.

  CUSTOMIZING THIS TEMPLATE (per project, permanent, team-wide)
  - Copy this file to `.specify/templates/overrides/review-template.md` and edit it there.
  - Commit it. Every review the command publishes from then on follows your structure, and the
    override survives `specify extension update`.
  - Add or remove sections as your process needs. A section you delete stays deleted; the command
    follows your version and says once what it had to place elsewhere.
  - Do NOT edit this file in place once installed under `.specify/extensions/`: the next extension
    update replaces the extension's files and your edit is lost.
-->

**The summary body.** Published as the review body. The command adds the anchor comment and the disclosure
line above it, and the coverage section below it.

## Summary

<!--
  Two to four sentences: what this PR does as you understand it, what you checked it against
  (spec, issue, constitution), and the headline. The author reads this first and sometimes only
  this. Do not repeat the findings here.
-->

[Summary]

## Blockers

<!--
  Findings that must be resolved before merge. Task items, because the author works through them —
  `- [ ]` renders as a checkbox on GitHub. Delete the section when there are none.
-->

- [ ] [1] [what is wrong] — `[file]:[line]`
      Source: [the quoted clause, requirement id, issue reference, or named principle]
      Impact: [why it matters] · Fix: [what to do about it]

## Major

<!-- Should be resolved; merging is consciously accepted debt. Also task items. -->

- [ ] [2] [what is wrong] — `[file]:[line]`
      Source: [source] · Impact: [impact] · Fix: [fix]

## Minor / Nits

<!--
  Real defects of bounded consequence, and style points where the project has stated a rule.
  Plain bullets, not task items — these may be deferred, and unchecked boxes on optional work
  read as outstanding obligations.
-->

- [3] [what is wrong] — `[file]:[line]` · Source: [source] · Fix: [fix]

## Questions

<!--
  Where the answer turns on intent only a human holds. Not defects. Plain bullets: there is
  nothing to tick, only something to answer.
-->

- [4] [the question] — `[file]:[line]` · Why it matters: [what turns on the answer]

## Acknowledged blocker — approved over

<!--
  Only when an approval consciously overrode a blocker. Name the finding and, if the reviewer gave
  one, the reason. Delete this section otherwise — its presence is a signal in itself.
-->

- [n] [the blocker that was accepted anyway]

**The inline comment.** One comment per finding whose anchor falls inside the diff. Posted on the line
itself, so it does not repeat the file and line — the position says that already. Keep it short: the
summary body carries the overview, this tells the developer what to change *here*.

**[SEVERITY]** — [what is wrong, in one or two sentences]

Source: [the quoted clause, requirement id, issue reference, or named principle]

Impact: [why it matters]
